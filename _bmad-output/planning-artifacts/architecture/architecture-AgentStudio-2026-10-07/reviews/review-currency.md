## Findings by severity

### HIGH

None. No named technology is stale, retired, misversioned, or misassigned. Notably, the three claims most likely to be hallucinated from stale training data — the MCP revision date, the OTel GenAI repo-move date, and the existence of `DBOSDurability` — are all independently confirmed correct. This spine was reality-checked, not asserted.

### MEDIUM

**MED-1 — "Pydantic AI 2.x" is too wide a band to be a pin. (VERIFIED)**
The library is at **2.54.0**, from 2.0.0 on 2026-06-23 — roughly 54 minors in 15 weeks. The vendor's own [version policy](https://github.com/pydantic/pydantic-ai/blob/main/docs/version-policy.md) does commit that "we will not intentionally make breaking changes in minor releases," and deprecated functionality survives to the next major (no sooner than 3 months after 2.0) — so `2.x` is *semantically* safe. But the policy explicitly exempts from "breaking": bug fixes to undocumented behaviour, new optional fields on message types and events, and **changes to OpenTelemetry span attributes**. The third exemption lands directly on the spine's own evidence vocabulary convention, and the second lands on the serialized message history the deferred-tool resume path depends on. Recommend the Stack table state a floor and a tested ceiling (e.g. `>=2.54,<3`) rather than `2.x`, and that the proof gate record the exact version it was proven against.
*Also:* anything in a `beta` module is explicitly outside the stability promise. If the proof gate reaches for a beta module, say so.

**MED-2 — The DBOS atomicity guarantee is datasource-scoped, and the spine should say which decorator carries it. (VERIFIED mechanism; INFERRED consequence)**
The spine's AD-12 and the sequence diagram ("write evidence + result in one durable step") rest on checkpoint/write co-commit. That is real, but it attaches to a **datasource transaction** — `@ds.transaction()` on a datasource instance — **not** to `@DBOS.step`, and **not** to `@DBOS.transaction` (which the Python docs do not show). An ordinary step calling an HTTP extension gets at-least-once with a *separately* committed checkpoint, not atomicity — which is exactly why AD-10's idempotency key is load-bearing and should be read as the *only* protection for non-Postgres effects. Further: DBOS takes `APP_DATABASE_URL` and `DBOS_SYSTEM_DATABASE_URL` separately, so the two can be different databases — in which case a single Postgres transaction cannot span both and the co-commit property does not hold. **Recommendation:** at platform-initiative altitude, add one line to the Deferred "Durability engine selection" row: *evidence and effect co-commit requires the evidence store and the application store to be the same Postgres database.* That is an architectural constraint, not an implementation detail, and a builder cannot guess it.

**MED-3 — PostgreSQL is named with no version, and the DBOS dependency makes that a guess. (VERIFIED absence)**
The Stack table says "PostgreSQL," full stop. DBOS publishes no minimum major that I could find, and the spine's declared fallback floor — "Postgres tables with a unique constraint on `(episode, step, idempotency key)`" — needs nothing exotic. But the spine also wants durable queues, `LISTEN/NOTIFY`-style notification, and (per the Deferred retrieval row) possibly `pgvector` later. A builder standing up infrastructure today has to pick a major. Name one. **Postgres 16+ is the defensible floor** (INFERRED, not vendor-mandated): it is what every managed provider DBOS lists offers by default, and it keeps `pgvector` and modern logical-replication options open without pinning to a version whose support window is short. State it as a floor with the reason, so the proof gate inherits a decision rather than an accident.

### LOW

**LOW-1 — The Python floor is fine; note that 3.12 is security-only. (VERIFIED)**
3.12 left active bugfix support and is in security-only mode; 3.13 and 3.14 are the actively maintained lines, and **3.15.0 ships tomorrow, 2026-10-09**. Both dependencies accept `>=3.10`, so `3.12+` constrains nothing and breaks nothing. It is a correct, conservative floor and I do not recommend changing it at this altitude. One advisory: a *floor* of 3.12 is not the same as a *target*; if CI is going to run one interpreter, run 3.13 or 3.14. And given 3.15 lands within 24 hours of this review (UTF-8 default encoding, explicit lazy imports), do not let a reader infer from "3.12+" that 3.15 has been tried.

**LOW-2 — "Provider portability" is verified for the API surface, not for behaviour. (VERIFIED claim; judgement)**
The vendor claims code-change-free vendor swapping, and the `Model` abstraction delivers it. But v2.0's breaking-change list includes "OpenAI model names now use the Responses API" and "WebSearch and WebFetch are native by default" — i.e. provider-native capabilities whose availability is *not* uniform across the Model abstraction. AD-14 says changing the provider "must not alter the business agent architecture." That survives a provider swap at the type level; it does not survive a swap at the capability level if the agent ever depends on a provider-native tool. The spine already has the right escape hatch — AD-9's "the Core knows contracts, never vendors" — so this needs no new AD, only awareness that *provider-native tools are extensions and must be reached as extensions*, never as runtime conveniences. Worth one clause in AD-14.

**LOW-3 — MCP's statelessness is a real fit question the spine does not acknowledge. (VERIFIED facts; judgement)**
The 2026-07-28 revision the spine pins removed protocol-level sessions, the `Mcp-Session-Id` header, the `initialize` handshake, and SSE stream resumability (`Last-Event-ID`); "a broken response stream loses the in-flight request; clients MUST re-issue it as a new request with a new request ID." Servers needing cross-call state now use "explicit, server-minted handles passed as ordinary tool arguments." This is *good* for the spine — AD-13's episode identity and AD-10's idempotency key are precisely the right answer, and the removal of resumability makes AD-10 mandatory rather than prudent. Also relevant: **Sampling, Roots and Logging are now Deprecated** (12-month window), with the suggested migration for Logging being "use OpenTelemetry" — which aligns with the spine's evidence convention. No change required; one sentence in the Capability transport row noting that MCP 2026-07-28 is stateless *and that this is why episode identity lives in the Core, not the transport* would make the fit explicit rather than lucky.

**LOW-4 — Pin the MCP extension opt-in posture. (VERIFIED)**
Extensions are "always disabled by default and require explicit opt-in from the developer," and SDK support for any given extension is optional — "SDK maintainers have full autonomy over which extensions they support." If the authorization story ever leans on Enterprise-Managed Authorization, that is an SDK-support dependency, not a spec guarantee. Fine to leave deferred; do not let it read as available-by-default.

## Pinning judgement (altitude)

**Nothing is over-pinned.** Every row in the Stack table is either hedged in place (`candidate, behind AD-14`; `shortlisted, not committed`) or is a genuine invariant of the architecture (a protocol revision, a vocabulary, a store family). The header "**Seed, verified 2026-10-08. The code owns this once it exists**" is the correct device at initiative altitude and should be kept verbatim. Policy engine (OPA/Cedar), retrieval architecture, model routing and the V1 channel are all correctly in Deferred rather than pinned — each would be a decision made before its requirement exists.

**Under-pinned, in order of how much a builder would otherwise have to guess:**
1. The Postgres major (MED-3) — a builder cannot provision without choosing.
2. The evidence-store/application-store co-location constraint (MED-2) — an architectural property, currently invisible.
3. A tested Pydantic AI version range (MED-1) — `2.x` spans 54 releases.

**On the deliberate absence of a model and provider: this is right, and it is the single best judgement call in the Stack table.** AD-14 makes provider abstraction an invariant and demands only that "model tiering across capability classes must be expressible at this boundary" — a *structural* requirement, correctly pinned — while the Deferred table sends routing and tiering policy to evaluation as "measured, not designed." Naming a model in an initiative-altitude spine would (a) contradict AD-14's own prohibition on provider types crossing the boundary, (b) decay faster than any other line in the document, and (c) pre-empt the proof gate's latency and cost comparison before it has run. The live verification supports the abstraction's adequacy: the `Model` class is vendor-documented as making an agent "portable to different LLM vendors without any other code changes." Keep the omission. The only refinement is LOW-2: say that provider-*native* capabilities are extensions, so "unpinned provider" cannot be misread as "any provider, any capability."
