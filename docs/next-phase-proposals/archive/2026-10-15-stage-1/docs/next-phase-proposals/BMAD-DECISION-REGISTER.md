## 0. The audit

### 0.1 Two status axes, kept separate

The user asked for decision status and implementation status to be separable. They are different claims about different artifacts, and conflating them is how an implementation choice gets mistaken for a product approval.

**Decision status** — what the sources show about the decision itself:

| Status | Meaning |
| --- | --- |
| **APPROVED** | A source records the user making or confirming it: a quoted message in `DECISION-LOG.md`, or a `.memlog.md` entry attributing it to the user/operator (`(decision by user)`, `(override)`, `(direction) USER`, "user, binding", "operator ruling"). |
| **PROPOSED** | Stated in a final document or recommended by an assistant, with no recorded user confirmation. |
| **OPEN** | The sources say it is undecided, or they conflict and nobody ruled. |
| **SUPERSEDED** | Replaced by a later decision; the replacement is named. |

**Implementation status** — what the repository shows, from evidence gathered this session:

| Status | Meaning |
| --- | --- |
| **VERIFIED** | I ran a command or read the code this session. |
| **PARTIAL** | Some of the decision's substance exists; the gap is named. |
| **ABSENT** | Searched and not found; the search is named. |
| **UNVERIFIED** | Not checked this session. |
| **N/A** | Not a code-bearing decision (copy rules, market posture, process). |
| **DEFERRED** | A decision says not to build it. |

A document marked `status: final` is **not** treated as approval. An implementation choice made during the seven-day sprint is **not** treated as product approval. A previous assistant summary is **not** treated as evidence.
